# Langflix 일본어 버전 — 기술 아키텍처 설계안

> **2026-07-28 구현 변경:** 마이크 녹음·음성 인식·자동 발음 채점은 사용자 요청으로
> 보류했다. 현재 MVP는 `원음 듣기 → 구간 반복·오버랩 → 자막 없이 말하기 →
> 자기평가 → SRS 복습`이며, 아래 발음 채점·녹음 항목은 장기 설계 기록으로만 남긴다.

## Context

**무엇을 / 왜.** langflix.io(㈜세타원코리아)는 "유튜브·넷플릭스 이중자막 + AI 쉐도잉"으로 **영어**를 배우는 학습 앱이다. 이 문서는 동일한 학습 루프를 **일본어 학습**으로 옮긴 신규 제품의 기술 아키텍처를 설계한다. (기존 로컬 코드베이스 `jptaku-*`는 참고하지 않고 완전 신규로 설계.)

**확정된 결정 (사용자 선택).**
- 소스: **넷플릭스 + 유튜브 쇼츠** 2종 (라프텔 제외 — 우회 인프라 부재·일본어 자막 트랙 미제공·제휴 필요라는 3대 블로커 때문)
- 스택: **Flutter(앱) + Go/Gin(백엔드)**, 크롬 확장은 별도 TypeScript
- MVP 우선순위: **넷플릭스 확장 먼저**
- **AI 쉐도잉(발음 채점) MVP 포함**

**이 단계 산출물.** 코드 작성 없음. 프로젝트 디렉토리 구조 + 컴포넌트별 설계 + MVP 범위 정의까지.

---

## 학습 루프 (제품 흐름)

Langflix 영어판과 동일한 4단계 루프를 일본어로 이식:

1. **예습** — 해당 콘텐츠의 핵심 표현 레슨 선학습
2. **이중자막 시청** — 넷플릭스에서 **일본어 원자막 + 한국어 번역** 동시 표시, 마음에 드는 표현 탭→저장
3. **연습** — 앱에서 쉐도잉(녹음→발음 채점), 작문/퀴즈
4. **복습** — 망각곡선(SRS) 기반 저장 표현 간격 복습

넷플릭스 시청은 **PC(크롬 확장)**, 연습·복습·쉐도잉은 **모바일 앱** — 두 컴포넌트가 "저장 표현"을 통해 연결된다. 따라서 "넷플릭스 확장 우선" MVP라도 쉐도잉을 위해 **앱은 필수 동반**된다.

## 컴포넌트별 설계

### 1. 크롬 확장 (MVP 핵심, TypeScript · Manifest V3) — 넷플릭스 + 유튜브
- **역할**: 웹플레이어 위에 일본어 원자막 + 한국어 번역 2줄 오버레이, 표현 하이라이트, 탭→저장.

#### 1-1. 사이트 어댑터 구조 (핵심 설계)
확장 코드의 대부분은 **사이트와 무관한 공통 레이어**이고, 사이트별로 갈리는 것은 **"자막 cue를 어디서 얻는가"와 "재생 시각을 어떻게 읽는가"** 뿐이다. 이 둘만 `SubtitleSource` 인터페이스 뒤로 분리한다.

| 구분 | 내용 |
|---|---|
| **공통(재사용)** | 오버레이 렌더러, 번역 클라이언트, NLP 하이라이트, 뜻풀이 툴팁, 표현 저장/백엔드 동기화 |
| **어댑터별** | cue 취득 방식, 플레이어 핸들(`currentTime`), 오버레이 부착 지점, SPA 전환 감지 |

```
SubtitleSource (interface)
  ├─ YouTubeAdapter   ← youtube.com/watch + youtube.com/shorts
  └─ NetflixAdapter   ← netflix.com/watch
```

- **YouTubeAdapter**: 페이지의 player response에서 `captionTracks`를 확보해 timedtext(json3) cue 목록을 가져온다. 일본어 트랙(`ja`) 우선(정식 자막 > 자동생성). 쇼츠 URL도 동일 어댑터로 커버.
- **NetflixAdapter**: 공개 API가 없으므로 **플레이어가 이미 내려받는 자막(timedtext, TTML/XML)을 가로채/파싱**. `content script`(격리 환경)에서 페이지에 `injected script`를 주입해 네트워크 응답 또는 플레이어 상태에서 cue(`{start, end, text}`) 확보.

#### 1-2. 개발 순서 — **유튜브 PoC 선행**
넷플릭스는 유료 구독·DRM·플레이어 통제 때문에 초기 개발 난이도가 높다. 따라서 **파이프라인 전체(cue → 번역 → 형태소/후리가나/JLPT 하이라이트 → 표현 저장)를 유튜브에서 먼저 검증**한 뒤, 검증된 공통 레이어에 `NetflixAdapter`만 갈아끼운다.

| 항목 | 유튜브 | 넷플릭스 |
|---|---|---|
| 계정/구독 | 불필요 | 유료 구독 필요 |
| 자막 접근 | 캡션(timedtext) 상대적 개방 | 플레이어 내부에서 가로채기 |
| 플레이어/DOM | 다루기 쉬움 | 통제 강함(오버레이 덮어쓰기) |
| DRM | 사실상 무관 | 영상 DRM(자막은 별개나 환경 까다로움) |

> 이는 **개발·테스트 전략**이며 로드맵 변경이 아니다. Phase 2의 "유튜브 쇼츠 **인앱**(모바일) 플레이어"는 그대로 유지된다. 확장의 유튜브 지원은 별도 산출물이며 추후 PC 정식 기능으로 승격 가능.

#### 1-3. 기타
- **번역 라인**: 확보한 일본어 cue를 백엔드에 보내 **일→한 번역(사전 번역·캐싱)** 을 받아 두 번째 줄로 표시. 플랫폼이 한국어 자막 트랙을 함께 제공하면 그걸 우선 사용, 없으면 LLM 번역.
- **표현 하이라이트**: 백엔드 NLP가 분석한 단어 경계 + JLPT 레벨을 이용해 사용자 레벨에 맞는 표현 강조, 클릭 시 뜻풀이 툴팁 + "복습에 추가".
- **핵심 난제 & 대응**:
  - *SPA*: 두 사이트 모두 페이지 리로드 없이 전환 → 플레이어 재감지·재초기화(MutationObserver / 네비게이션 이벤트)
  - *싱크*: 배속/버퍼링/seek마다 `currentTime` 기준 재보정
  - *플레이어 통제*: DOM 오버레이가 덮어써질 수 있어 별도 오버레이 레이어 유지·재부착
  - *DRM(넷플릭스)*: 영상은 DRM 보호되나 자막 텍스트는 별개라 취득 가능
  - *쇼츠 자막 품질*: 정식 자막 없이 자동생성에 의존하는 경우가 많음 → 초기 검증은 **일본어 자막이 달린 일반 영상**으로, 쇼츠는 그다음

### 2. Flutter 모바일 앱 (MVP 포함, iOS/Android)
- **온보딩**: 목표 레벨(N5~N1), 관심 장르 선택
- **레슨(예습)**: 콘텐츠별 핵심 표현 카드
- **표현 라이브러리**: 확장에서 저장한 표현 목록 (백엔드 sync)
- **복습(SRS)**: 망각곡선 스케줄로 카드 노출
- **쉐도잉(MVP)**: 원어민 오디오 재생 → 사용자 녹음 → 발음 채점 결과 표시(정확도·유창성). 녹음은 Object Storage 업로드 후 채점 프록시 경유
- **유튜브 쇼츠 플레이어**: **Phase 2** (인앱 플레이어 + 캡션 이중자막)
- **기술**: Riverpod(상태), Go Router, Dio, 오디오 녹음 플러그인

### 3. Go/Gin 백엔드 (MVP 포함)
- **역할**: 인증, 표현 저장/동기화, SRS 스케줄링, 레슨 CRUD, 번역/채점/NLP **프록시 및 캐싱**
- **구조**: 4계층(미들웨어 → 핸들러 → 서비스 → 리포지토리)
- **엔드포인트(초안)**: `/auth`, `/expressions`(CRUD+sync), `/reviews`(SRS due/submit), `/lessons`, `/translate`(캐시 우선), `/nlp/analyze`(프록시), `/shadowing/score`(프록시)
- **인증**: Google OAuth (확장·앱 공용 토큰)

### 4. Python NLP 마이크로서비스 (MVP 포함, FastAPI)
- **왜 별도 언어**: 일본어는 띄어쓰기가 없어 **형태소 분석이 모든 단어 단위 기능(탭·저장·하이라이트·후리가나)의 전제**인데, 고품질 일본어 NLP 생태계는 Python/Java에 집중. Go 단독은 품질 한계.
- **구성**:
  - 형태소 분석: **Sudachi**(문맥 기반 읽기 해석) 또는 MeCab+UniDic
  - **후리가나**: Kuroshiro(+kuromoji) 또는 Sudachi 기반 서비스
  - **JLPT 레벨 태깅**: JMdict/JLPT 어휘 목록 매핑
  - **사전**: JMdict 뜻풀이
- **인터페이스**: `POST /analyze` → 문장 입력 → `[{surface, reading(furigana), lemma, jlpt, gloss}]`
- **대안(경량화 옵션)**: 순수 Go **kagome**를 백엔드 내장 → 서비스 1개 축소 가능(단 후리가나/JLPT/사전 품질은 Python 대비 열위). 설계는 NLP를 인터페이스 뒤에 두어 **나중에 교체 가능**하게 유지.

### 5. 자막·미디어 파이프라인
- **넷플릭스**: 자막 취득은 **클라이언트(확장)** 가 담당. 서버는 번역·정규화·캐싱만 → 서버가 넷플릭스에 직접 접근하지 않아 리스크·부하 감소
- **유튜브 쇼츠(Phase 2)**: 서버가 캡션(timedtext) 취득 → 없거나 자동생성 품질이 낮으면 **ASR(Whisper) 폴백**으로 일본어 자막 생성
- **번역**: 일→한은 LLM(문맥 반영) + **사전 번역·Redis 캐싱**으로 지연/비용 최소화

### 6. 발음 채점 (MVP 포함, 외부 API)
- **후보**: Azure **Pronunciation Assessment**(일본어 지원, accuracy/fluency 점수 — 단 일본어는 음소 단위 결과가 비는 알려진 한계) vs **SpeechSuper**(히라가나/가타카나/한자·음소 단위 채점 강점)
- **MVP 권고**: 문장 단위 accuracy/fluency 채점부터 도입. **일본어 고저악센트(pitch accent) 정밀 채점은 Phase 2** 로 분리(별도 pitch contour 분석 필요, 난이도·비용 큼)
- 설계상 채점기를 인터페이스 뒤에 두어 공급자 교체 가능하게 유지

## 데이터 모델 (주요 엔티티, 초안)
- **User** — 인증, 목표 레벨, 관심 장르
- **ContentRef** — 넷플릭스 title/episode 식별(플랫폼, 외부 ID, 제목)
- **Expression** — 저장 표현(surface, reading, gloss, jlpt, 출처 ContentRef+타임코드)
- **Lesson** — 콘텐츠별 예습 표현 묶음
- **ReviewCard** — SRS 상태(ease, interval, due_at) — Expression 참조
- **ShadowingAttempt** — 녹음 URL, 채점 결과(accuracy/fluency), 타임스탬프

## MVP 범위 vs 이후

**MVP (넷플릭스 우선 + 쉐도잉 포함)**
- 크롬 확장: **① 유튜브 어댑터로 PoC 선행(파이프라인 검증) → ② 넷플릭스 어댑터 추가**. 일→한 이중자막, 표현 하이라이트/저장
- Flutter 앱: 온보딩, 레슨 예습, 표현 라이브러리, SRS 복습, 쉐도잉(녹음→문장 채점)
- Go 백엔드: 인증, 표현 sync, SRS, 번역/채점/NLP 프록시+캐시
- Python NLP: 형태소·후리가나·JLPT·사전
- 발음 채점: Azure/SpeechSuper 문장 단위

**Phase 2 이후**
- 유튜브 쇼츠 인앱 플레이어 + ASR 폴백
- 고저악센트 정밀 채점
- 유튜브 링크→코스 자동생성
- 결제(구독) · "다른 장면"(표현별 다중 예문)

## 검증 방법 (구현 후 E2E)
1. **확장**: 넷플릭스 일본어 콘텐츠 재생 → 일→한 이중자막 표시, 배속·seek 시 싱크 유지, 표현 탭→저장 확인
2. **동기화**: 확장에서 저장한 표현이 앱 라이브러리에 나타나는지 확인
3. **NLP**: `POST /analyze` 에 일본어 문장 → 형태소·후리가나·JLPT·뜻풀이 반환 검증
4. **쉐도잉**: 앱에서 원어민 오디오 재생→녹음→채점 점수(accuracy/fluency) 반환 확인
